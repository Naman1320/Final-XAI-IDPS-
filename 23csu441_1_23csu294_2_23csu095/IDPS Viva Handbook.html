1. Complete project understanding

The project in one example. A sensor converts a network conversation into a row of measurements. A classifier gives that row a label and a confidence score. A policy decides whether the evidence warrants a response. The dashboard lets a person see the alert, investigate it, and check what the firewall actually did. In the archived C6 classroom replay, 41 lab detections led to a recorded firewall change. A separate cloud pipeline recorded 57 alerts and one block decision, and an AWS CLI query read the resulting deny entries from a local emulator.

Examiner’s question What the team can defend
Why build it? An operator can have a suspicious flow, a model score and a firewall rule on three different screens. The project brings prediction, explanation and response evidence into one investigation.
What problem does it solve? It helps an analyst decide which traffic deserves attention, understand why the model scored it highly, and distinguish a proposed block from a verified state change.
What are the objectives? Classify flows, measure errors on public data, test whether explanations identify influential features, apply a guarded response, and show its outcome and timing. Each objective has a different test.
What is the motivation? Both mistakes matter. A missed attack can leave a network exposed. A mistaken block can disconnect a legitimate service. This motivates class-level evaluation, allowlists, dry runs and expiration.
What is the existing system? The defensible comparison is with components: Suricata supplies rule/signature alerts, a flow classifier supplies statistical predictions, and a firewall enforces rules. The project includes comparisons with Suricata. There is no supplied before-study of a particular university’s earlier SOC.
What limitations prompted the design? A rule can cover known patterns while missing unfamiliar behavior. A model can fit patterns specific to its training capture. A firewall rule alone does not explain which observation triggered it. Each limitation needs its own evidence.
What is proposed and implemented? A lab sensor, an explainable model, a policy engine, a cloud flow-log collector, a SOC API and database, an analyst dashboard and a locally reproducible evidence workflow. Some integrations need separate credentials or services.
What is the contribution? Integration and evaluation: comparable experiments on three datasets, explanation deletion tests, guarded response and an auditable classroom replay. XGBoost, SHAP, LIME and nftables are existing technologies.
Where could it be used? Teaching network security, evaluating detection strategies offline, or piloting monitoring on an authorized network. A pilot would first measure local errors and operating costs in dry-run mode.
What is the boundary? Separate the recorded benchmark, the archived local replay, the current state of a running service and a future production deployment. Each supports a different claim.

2. Technical explanation

Architecture in plain English

Imagine receiving a parcel at a warehouse. The scan record describes what arrived, a rule determines what should happen, and a signed receipt tells you what actually happened. In this project those records correspond to a flow, a decision and a read-back. They can disagree. A suspected flow can be allowlisted, and a proposed block can fail.

Offline evaluation
Public flow data → clean, label, split → train → held-out scores and explanation tests

Lab data plane
Packets or saved PCAP → flow extractor → model bundle → detection
                                            ├→ local policy → nftables → state read-back
                                            └→ alert outbox → SOC ingest → SQL database
Suricata EVE rule events ─────────────────────────────────→ SOC ingest
                                                                ├→ REST history
                                                                └→ live WebSocket → dashboard

Cloud evidence
Flow-log objects → collector → cloud-specific model → response policy → network ACL
                                                                          └→ ACL read-back

Classroom control
Dashboard → authenticated C6 API → evidence worker → stage reports → dashboard timeline

Read the three paths separately. The local sensor can act while a browser is closed. The SOC makes stored evidence available to multiple readers. C6 coordinates a particular demonstration. The Cloud Dashboard also has an inventory provider, which is separate from the cloud collector that makes ACL decisions.

Three experiments and what the numbers mean

Dataset Processed rows / test rows, with ports Classes Accuracy Macro-F1 Benign false-positive rate
CIC-IDS2017 1,333,655 / 265,288 9 94.4% 0.795 6.8%
CSE-CIC-IDS2018 1,574,057 / 316,775 7 72.3% 0.802 34.3%
UNSW-NB15 545,644 / 110,715 10 96.1% 0.708 1.2%

Use the idps.public comparison rows. The same report contains a separate CIC week pipeline with different classes and features. Nine of ten 2018 capture files were used. Each dataset has a separately trained model and distinct class mix. A class-time split takes earlier examples for training and later ones for testing within class. Short bursts can shrink the separating gap. Deduplication inside a split still permits identical rows across splits. The benign false-positive rate uses the deduplicated benign test set. A rate measured there cannot be directly converted to a real campus alert volume.

Worked example. Suppose 100 benign flows were evaluated and 5 were flagged. The false-positive rate would be 5%. The proportion of alerts that were false would need a different denominator: all alerts. This is a teaching example, separate from the measured table. Precision asks how many predicted positives are true. Recall asks how many actual positives were found. F1 is 2 × precision × recall / (precision + recall). Macro-F1 averages that score across classes, giving a rare class an equal vote.

Explanation experiment. On samples of 87, 98 and 100 test flows, SHAP’s five chosen features beat random feature selection on 95.4%, 96.9% and 90.0% of examples respectively. LIME’s figures were 41.4%, 62.2% and 73.0%. Replacing features with typical values tests model sensitivity. It does not reveal the real-world cause of an incident and replacement may create unusual feature combinations.

Transfer experiment. For seven shared CIC classes, the 2017-trained model scored 0.758 on its own held-out data and 0.469 on 2018. The reverse comparison was 0.794 and 0.287. These baselines use the same reduced features as their corresponding transfer models. The project did not cross-test UNSW against CIC because their schemas and label meanings differ. Sources: reports/public_datasets_comparison.json, reports/cross_2017_2018.json, docs/training-dataset1.md.

Database structure and queries

The inspected schema contains 35 application tables plus Alembic’s revision table. Use the appendix for every table, column and foreign key. A user can create cases; a case can have many notes and alerts. A sensor can submit many alerts. Group membership and role assignments use join tables. Policy attachments identify the subject type and ID. A cloud subnet belongs to a VPC; an instance can belong to multiple security groups through an association table. Audit history and login history answer different questions: “what changed?” and “who tried to sign in?”

The queries below were executed against a newly migrated empty SQLite database. They establish that the schema and SQL agree. Empty results are expected in that verification database.

-- Which labels generated alerts in the selected period?
SELECT predicted_class, COUNT(*) AS alerts_seen
FROM alerts WHERE received_at >= :cutoff
GROUP BY predicted_class ORDER BY alerts_seen DESC;

-- Which cases exist, including those with zero attached alerts?
SELECT c.id, c.title, COUNT(a.id) AS linked_alerts
FROM cases AS c LEFT JOIN alerts AS a ON a.case_id = c.id
GROUP BY c.id, c.title;

-- Which groups directly include the selected user?
SELECT g.name FROM iam_groups AS g
JOIN iam_group_members AS m ON m.group_id = g.id
WHERE m.user_id = :user_id;

The first query cannot estimate network-wide accuracy: benign flows normally never enter the alerts table, and unreviewed detections lack ground truth. The third query lists memberships; obtaining effective permissions additionally requires role grants, attached policies, resource checks and the admin exception.

3. Workflow from startup to output

  1. Start the right deployment. A Mac window is one client. Development and lab are different services with their own databases and identities. The classroom C6 launcher can run a separate temporary SOC. Select the one you intend to demonstrate.
  2. Open the application. The frontend loads its compiled assets and chooses its workspace from the path. Development and lab use different API prefixes and session keys. The iPhone adds an outer Google identity check through ngrok.
  3. Sign in. The API verifies the password and current user, issues the appropriate challenge or session token, and checks account status again on protected requests. The browser handles a rejected session by returning to sign-in.
  4. Receive a flow. A flow extractor summarizes packets. The model bundle selects the expected features and runs inference. A rule event can reach the SOC via its own path. A cloud flow-log record uses a different model.
  5. Evaluate the prediction. The sensor identifies non-benign rows, applies thresholds and allocates limited explanation work. The response policy considers the normalized source, protections, confidence and accumulated evidence.
  6. Decide or observe. The policy may observe, reject, retain an existing block, or request a timed block. Dry-run mode records what would happen. The blocker implements the side effect. An independent read-back is the strongest evidence for the demo.
  7. Persist and deliver. The sensor’s outbox allows scoring to continue through temporary delivery problems. Ingest commits accepted alerts and their audit event before broadcasting. Notifications are optional and queued separately.
  8. Investigate. The client displays alert details and explanations, supports analyst labels and case notes, and lets authorized operators see response and audit records. Browser navigation is never the final permission check.
  9. Finish or report the exception. Missing optional explanation data, an unavailable worker, a full subscriber queue and a failed database commit have different effects. Explain the failing boundary. Show the recorded fallback if a fresh demonstration cannot finish.

Decision flowchart for the board

Detection enters policy
   ├─ malformed address or protected address? → invalid or protected decision
   ├─ benign prediction or insufficient confidence? → stop or observe
   ├─ active block still valid? → record already blocked
   ├─ insufficient qualifying flows in the window? → continue observing
   └─ criteria met → timed block decision
                       ├─ dry run → would-block evidence
                       └─ enforcement enabled → apply → check actual state

A check on the candidate IP precedes any automatic effect. In the diagram, “stop” means this policy evaluation ends. It does not stop the sensor.

8. Weaknesses, improvements and honest defenses

Finding and scope Why it matters Realistic improvement and verification
Relocated Python package. Root packaging still discovers idps* and soc* from the original layout. Root documentation also references the former docs path. A fresh interpreter, packaging job or Docker build can miss the moved tree even if an already-running service works. Update package discovery, copy contexts and links coherently; then test a clean wheel and both container builds. For this review the project root and team submission directory were added to PYTHONPATH.
Dataset shift and short temporal gaps. Transfer scores and data notes provide direct evidence. Similar rows and capture-specific features can inflate confidence. Gaps shrink within short class bursts. Hold out sites, sessions and tools; test several seeds and report class-level uncertainty. Keep the current scores labeled by dataset and split.
Benign false positives. On the 2018 deduplicated test set 34.3% of benign flows were flagged. Too many false alerts create work; a policy can still block the wrong source. Calibrate per-class thresholds and validate the combined classifier-and-policy false-block rate on reviewed local traffic.
Process-local state. Broadcaster, C6 slot and several throttles live in app.state. Restarts discard run state; multiple workers can disagree on availability, limits and events. Persist runs with uniqueness/lease rules, move fan-out to a shared bus and test cross-worker consistency and restart recovery.
Bounded queues and possible duplicates. Slow subscribers may be dropped. Ingest does not show a stable source-event uniqueness constraint. Delivery under backpressure or an ambiguous acknowledgement can lose or duplicate observations. Add event IDs, deduplication and client catch-up cursors; test a deliberately interrupted acknowledgement in a benign fixture.
Browser token exposure. sessionStorage is accessible to same-origin JavaScript. This is a threat-model observation; no working injection was established in this review. An unsafe rendering change or compromised script could expose a session. Review rendering sinks, dependencies and CSP; weigh an HttpOnly cookie design together with CSRF protection and workspace separation.
Legacy admin exception and manual approvals. An authentic legacy admin bypasses policy denies. The manual decision handler accepts AnyUser and lacks a visible distinct-requester condition. Compromise has broad impact. The design does not establish independent two-person approval. Review which actions require separate approvers, enforce them server-side, limit privileged accounts and test the policy explicitly.
SQLite and database availability. WAL/busy handling assists local use, but cannot establish a production throughput guarantee. Contended writes or downtime delay durable ingest. The preparation run did not exercise its optional PostgreSQL cases. Benchmark realistic readers/writers on PostgreSQL, monitor slow queries and test backups, restores and outage recovery.
Explanation cost and availability. Computing SHAP for every suspicious row can be expensive. The live path uses an explanation budget. An absent explanation does not imply an absent detection. Processor load changes the timing. Publish budget-hit rates, tail latency and class coverage; compare cached/static explanations only where their semantics remain valid.
Emulator validity. A saved Moto ACL response verifies configuration. A single run does not establish cloud enforcement, billing or production latency. An examiner may confuse the writable mock inventory, the read-only emulator dashboard and the collector’s ACL response. Label each source. For a later authorized cloud trial, independently measure configuration propagation, packet outcomes and cleanup.
Personal attribution and deployment evidence. All-module involvement is self-reported; test logs and code establish behavior, not exclusive authorship. Claiming an unmeasured scale or another contributor’s decision is easy to challenge. Bring one personally authored change, one failed result and one test. Credit teammates explicitly.

9. Final revision notes

Twenty answers to remember

  1. The unit of classification is a flow. A packet, a flow, an alert and a block are four different units.
  2. A prediction is the model’s judgment. A policy decision is a rule evaluation. A read-back checks resulting state.
  3. The project combines learned flow patterns and rule-based evidence. Their labels and evidence sources can differ.
  4. The public experiments trained separate XGBoost models using dataset-specific features and labels.
  5. CIC-IDS2017 scored 0.795 macro-F1, CSE-CIC-IDS2018 scored 0.802 and UNSW-NB15 scored 0.708.
  6. UNSW had 96.1% accuracy. Macro-F1 gives the rare classes equal weight and was considerably lower.
  7. On deduplicated 2018 benign flows, 34.3% were flagged. False-positive rate uses all benign flows as its denominator.
  8. Macro-F1 on the seven shared classes fell to 0.469 and 0.287 in the two CIC transfer directions.
  9. Time-aware splits reduce leakage. Repeated patterns and short bursts can still affect the estimates.
  10. The deletion test compares the confidence drop from the explainer’s top five features with five randomly selected features.
  11. SHAP beat random on 95.4%, 96.9% and 90.0% of the respective sampled flows. This establishes sensitivity of the fitted model.
  12. Policy checks address validity and protections before confidence, window counts and expiry.
  13. The sensor can enforce locally and buffer outgoing alert delivery if the SOC is temporarily unavailable.
  14. SOC ingest writes rows and audit information before it publishes new-alert events.
  15. Identity and permission are distinct. For ordinary users an applicable deny wins; legacy admin is an explicit exception.
  16. Mock inventory writes update SOC tables. The dashboard’s emulator provider is read-only. The C6 collector has its own response path.
  17. The saved replay observed 41 lab detections, 57 cloud alerts and one cloud block decision. These counts describe different stages.
  18. The replay took 7.08 seconds and used Moto. It cannot establish live AWS latency or packet enforcement.
  19. Live fan-out and the C6 slot are process-local. Multiple workers require external coordination.
  20. The most defensible next step is a shadow-mode trial on fresh authorized traffic, with per-class recall, false blocks and repeated timings.
